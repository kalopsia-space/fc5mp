## P0.5 — manual disassembly of the partner functions

Disassembled `DoSpawnPlayer` (`0x18a169c30`) and `CreateCoopLeash` (`0x18a896770`) over their full extents. Findings:

**The `cmp …, 1` values are refcount releases, not partner logic.** Every one follows the pattern `lock xadd dword ptr [reg+8], eax` → `cmp eax, 1` → conditional `call <dtor>`, i.e. an atomic reference-count decrement detecting the last reference (shared-pointer / handle release). DoSpawnPlayer has 3, CreateCoopLeash has 9 — all boilerplate, none about player count. My earlier "boolean one-partner" reading of these was wrong.

**The `cmp …, 4` is a global config byte, not an array bound.** It disassembles to `cmp byte ptr [rip - 0x51bb4ba], 4`, targeting a global at VA ≈ `0x184FAE590` (a data-region byte), compared early in the function. It gates some mode-dependent path; it is not a player-array capacity.

**The one real player/entity collection is a dynamic, runtime-sized vector — not a fixed 2-slot array.** At `0x18a169ec7`–`0x18a169f04`:
```
lea r10, [rsi + 0xc0]      ; a container embedded at object offset 0xC0
mov rax, [r10]             ; begin pointer
mov rcx, [r10 + 8]         ; packed {flags:1, size:31} in the high dword
shr rcx, 0x20 ; btr ecx,0x1f  ; size = high dword with bit31 cleared
lea r8, [rax + rcx*4]      ; end = begin + size*4   (4-byte elements)
...                        ; second copy computes the same end into r9
cmp rax, r9                ; begin == end ? (empty check, start of an iteration)
```
This is the engine's standard growable-array idiom: `{T* begin; packed size}` with 4-byte elements (entity/handle IDs), iterated `begin…begin+size`. The width is **whatever the container holds at runtime**, set by code that fills it — there is no compile-time 2.

**No `cmp …, 2` cap exists** in any of the four resolved co-op functions (DoSpawnPlayer, CreateCoopLeash, CoopPartnerReady, CoopPartnerDetected). A hardwired two-player limit would almost certainly surface as such a compare in the spawn/partner paths; it does not.

## GATE DECISION: **QUALIFIED GO**

On the question P0 set out to answer — *is co-op player/entity storage a generic N-wide container (GO) or fixed 2-slot arrays (STOP)?* — the evidence is **GO**: the co-op spawn path iterates a dynamic runtime-sized vector of 4-byte handles, uses refcounted handles throughout, and contains no fixed-2 comparison. The specific STOP condition this gate guarded against is not present.

This is "qualified" because it narrows, but does not eliminate, the spec's blocker #2:
- **What this clears:** the fear that player data is baked into immovable 2-element structures. It is not; the engine uses dynamic containers, and Versus already drives the same lower-level netcode with up to 12 players.
- **What remains (now framed as logic, not a data wall):** widening is about (a) the Ubisoft-side session-admission cap — which this whole project replaces with its own server — and (b) game-RULES logic that assumes one partner (leash tether, revive, HUD markers, mission-start voting, objective/AI scaling, and — critically — whether the host's replication layer *registers* a 3rd/4th remote peer). These are code paths to widen, supported by the finding that the underlying storage does not block them.

Proceed to P1 (interception harness + live protocol capture). The remaining widening questions are best answered against a **running** game, where the player container at object offset `0xC0` can be inspected live and a real 2-player session shows exactly what the host registers per peer.

### Still-open (do not block P1)
1. **Live re-validation under Denuvo.** All of the above is static; on-disk bytes of protected regions may differ at runtime. Confirm the container and the absence of a 2-cap live in P1.
2. **Scanner coverage** (the 3 `no-xref` anchors) — secondary `.code` region + LEA-validated non-NUL string copies. No longer gating, but will resolve the leash-callback and Versus anchors for completeness.
3. **The `0x184FAE590` global** and the player-capacity constants (`nMaxNumPlayers`, `MaxPlayers`) — resolve to their structures to know where the admission cap is read.
4. **The "add player to session" path** (`CStormEchoAddSessionPlayerOp`, `CCoopServiceNetObjectP2P`) — the most direct view of per-peer registration, to confirm it loops over a dynamic peer set rather than a 2-slot one.

### Next steps (before the gate can close)
1. **Widen scanner coverage:** scan the secondary `.code` region for `lea` xrefs, and accept LEA-validated string copies regardless of NUL-prefix. Re-run; expect the 3 `no-xref` anchors to resolve.
2. **Manually disassemble the two resolved partner functions** — CreateCoopLeash `0x18a896770` and DoSpawnPlayer `0x18a169c30` — to read how the partner/player is stored and what the `cmp …, 4` gates. This is the single most informative next action.
3. **Find and read the "add player to session" path** (`CStormEchoAddSessionPlayerOp`, `CCoopServiceNetObjectP2P`) to see the container that holds remote players and whether its width is a constant 2.
4. **Resolve the player-capacity constants** (`nMaxNumPlayers`, `MaxPlayers`) to their defining structures.

## Confidence & caveats

- **Static only.** `FC_m64.dll` carries Denuvo markers; the on-disk bytes of protected regions may differ from what executes. The QUALIFIED GO must be re-validated at runtime in P1 before widening work begins.
- **Scope of the read.** The GO rests on four co-op functions plus one container-iteration site read by hand. It establishes the engine's container *style* (dynamic, refcounted, no fixed-2), which is strong structural evidence, but it has not traced the full player lifecycle end to end. P1's live inspection is where that gets nailed down.
- The toolkit's building blocks (VA mapping, function table with chain-info resolution, LEA scanner, anchor resolution, call graph, operand probe) are unit-tested against this exact DLL build and are reusable for P1.
